# Peekalo

Peekalo is being built as a camera-first photo/video sharing app: capture a photo or video up to ten seconds, then send it to selected accounts or share an anonymous single-use link. Recipients hold to reveal hidden media, with up to ten seconds total viewing time.

Peekalo has separate web applications: `apps/site` is the prelaunch marketing website; `apps/web` is the product web app with shared-link viewing, sample profile and local viewer demo. They share branding and browser UI through workspace packages and use the same backend. Mobile has Inbox, a prominent center Camera button, Profile and the same sample interaction. Try PHOTO-01 at `/s/demo` on web or “Explore this sample” from the mobile Profile. Hold reveals a public still-life illustration; release, cancel, movement outside, navigation or loss of foreground hides it. Every hold shares ten seconds, with a countdown and an exhausted state. Space/Enter work on web; an accessible “Reveal for 1 second” button uses the same allowance on both platforms. Opening the viewer does not spend time. The runtime keeps the sample allowance across route changes; page reload/app restart resets it. This is a local interaction prototype, not a real single-use link or server authorization.

The fixture's clear and physically downsampled/blurred PNGs are separate. Only the hidden asset renders before a hold. Both are identified non-sensitive demo assets and are publicly bundled; their source illustration is in `packages/reveal/fixtures/morning.svg`. This exception is solely for the sample. Private user media uses the separate authorized delivery gateway. The demo does not prevent screenshots or retained bytes.

Tap the shutter for a photo; hold it for 300 ms to start video and release to stop. Video stops at ten seconds using a native duration limit plus a JavaScript fallback. The first hold requests microphone access if needed; after granting it, hold again to record. Review supports photo viewing or video play/pause, plus Retake and Discard. Captured photos are center-cropped to exact 9:16.

Photos and videos originate only from the in-app camera; there are no gallery, photo-library or file imports. Drafts stay in app cache without saving to the photo library. Retake/discard, navigation away and backgrounding clear the draft and attempt cleanup; late capture results are invalidated and cleaned up. Cleanup is best effort, not a guarantee that delivered or stored bytes are erased. Samsung framing and video are user-confirmed; ten-second duration, audio, interruption, permission-denial and front-camera checks, plus physical iOS capture, remain pending.

## Prelaunch marketing site (MKT-01 / WEB-SPLIT-01)

These marketing assets do not verify protected delivery or native privacy. Early-access collection is **closed by default**. The page shows “opens soon” and `POST /api/waitlist` returns a sanitized 503 until `WAITLIST_ENABLED=true` is explicitly configured. The waitlist migration is deployed, but do not enable collection until real Supabase POST/duplicate behavior is verified and a working private contact/removal route is included in `/privacy`. Branded email is selected after domain choice; no domain or contact mailbox has been provisioned yet. Opening collection does not send emails or provide unsubscribe delivery; connect that flow before sending updates.

When enabled, the browser posts `{email, consent:true, website:""}` to the marketing site’s same-origin `/api/waitlist`. Its bounded server proxy forwards only this waitlist request to the configured product backend. The backend validates the exact `PUBLIC_SITE_URL` origin and saves to Supabase using its server-only service credential. `PUBLIC_APP_URL` remains a legacy origin fallback when `PUBLIC_SITE_URL` is absent. Both servers must explicitly enable `WAITLIST_ENABLED=true`; the marketing app receives no database credentials or private viewer/auth proxy routes. `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` stay in ignored server configuration. Duplicate requests return the same success and preserve the original consent record. No email, IP, request body or provider error is logged. RLS denies anonymous/authenticated database access. The body is capped at 2048 bytes and five seconds; storage requests have a five-second deadline. Identifier-free admission allows up to four in-flight requests and 30 requests per rolling minute per process. Limits reset on restart and do not coordinate across instances; use trusted edge limits before scaling. The flag is read at request time by the marketing page/proxy and backend endpoint. Keep protected/demo routes noindexed; search indexing for a public launch is a separate hosting change.

Run `pnpm test:waitlist` for the backend handler and disposable PostgreSQL permissions/consent checks, and `pnpm test:web-split` for origin/proxy boundary checks, plus the workspace lint/typecheck and both web builds. The Free marketing preview is live with collection closed; this does not create a mailbox or establish waitlist readiness.

## Install and run

Use **Node 24.14.1** and **pnpm 11.25.0**. Exact application dependencies are pinned in package manifests and `pnpm-lock.yaml`.

```sh
pnpm install --frozen-lockfile
pnpm dev:site  # Marketing website, port 3100
```

In another terminal, run `pnpm dev:web` for the product web app on port 3101. Open [the website](http://127.0.0.1:3100), [the web app](http://127.0.0.1:3101), [the sample profile](http://127.0.0.1:3101/u/demo) or [the viewer demo](http://127.0.0.1:3101/s/demo). These public samples need no API keys; early-access collection stays closed by default. Configured protected links use the product origin’s `/s/view#…`; unknown viewer paths show an unavailable state.

For cross-app links, configure `PUBLIC_SITE_URL` as the marketing origin and `PUBLIC_APP_URL` as the product origin on both servers. Use distinct actual HTTPS origins without paths or credentials in production. Only development supplies loopback defaults (`http://127.0.0.1:3100` / `http://127.0.0.1:3101`); use those same origins in the browser when testing origin checks. Missing or invalid production configuration omits cross-app links or shows an unavailable state rather than inventing a domain. The product `/privacy` redirects to the configured website’s notice; equal origins are rejected to prevent a self-redirect. No ignored environment files were changed as part of this split; ensure an older local `PUBLIC_APP_URL` still points to the product server before generating links.

For the native app, install Xcode 26.2+ with an iOS simulator runtime and CocoaPods, then run:

```sh
pnpm ios
```

Select an iPhone simulator when prompted, or pass its name/UDID with `pnpm ios --device <simulator>`. This runner builds Debug **simulator** binaries. It generates ignored iOS files, installs Pods, places Xcode build output and temporary downloads under ignored `.cache/`, then uses Expo to install the binary and start Metro. Physical-device/release builds are a later verification task using the Expo CLI and signing configuration.

After installing the development build, JavaScript-only changes need:

```sh

```

`pnpm android --device` uses Expo's local Android build and lets you select a connected phone. On this Mac, the command-line Android SDK and Temurin JDK 17 are installed; the full Android Studio IDE and emulator are not required for USB phone testing. SDK 36, build-tools 36.0.0, NDK 27.1.12297006 and CMake 3.22.1 are installed. SDK/Java/Gradle files live on **Mac External**, which must remain connected.

New zsh Terminal sessions load the tools automatically. In an already-open terminal, run:

### Manual moderation and safety (REL-03)

Source uses manual pre-publication approval without an AI/filtering service purchase. Apply `202610290001_moderation_safety.sql` **after** REL-02's media-controls migration with uploads/sharing quiesced, then deploy the matching API and native clients. This migration intentionally moves existing ready moments and public usernames into pending review while retaining private objects, links, grants and spent budgets. Review the intended development inventory before rollout; do not silently deploy it against original phone sessions. Older gateways cannot safely implement the new workflow. The new gateway fails closed without its migration.

A newly processed capture returns `moderation_pending`; the native share panel retains its moment ID and can check approval without uploading again. Pending moments consume one of three active slots. Approved moments can create grants/links; rejected or taken-down keys cannot republish. Profile names are likewise pending before public lookup/sharing. Owner inventory distinguishes pending, rejected and taken-down moments and retains deletion controls.

Restricted operators are separate signed-in accounts explicitly allowlisted through database administration, never through client Auth metadata. In a controlled SQL session, an authorized administrator can `insert into public.peekalo_operators(account_id) values ('REAL_OPERATOR_ACCOUNT_UUID')` and later revoke with `update public.peekalo_operators set enabled=false where account_id='REAL_OPERATOR_ACCOUNT_UUID'`. These are instructional placeholders, not executable provisioning. Membership changes are audited; ordinary/service API table writes cannot promote an account. A reviewer cannot approve their own name or captures. `/operator` accepts a short-lived **account access token** in memory only; never enter an admin/service key, password or refresh token. Queue, deliberate private-media review, profile/media decisions, suspension, report responses and audit reads pass through allowlisted RPCs. Clear review bytes use authenticated no-store delivery, with a second authorization check after Storage IO, never public/signed original URLs. Even authorized operators can retain delivered bytes; operational access discipline remains required.

`/safety` publishes Peekalo's CSAE/community standards, `/support` shows real configured contact details or an explicit closed-beta/pending state. Set `SAFETY_SUPPORT_EMAIL`, `SAFETY_CHILD_SAFETY_EMAIL` and `SAFETY_AGE_POLICY` only after human choices and real monitored delivery are verified. They are public operational values, not credentials. Configuration alone does not establish a designated responsible person, response coverage, legal escalation/reporting arrangements, age screening or invite enforcement. These remain release gates. Before opening an external beta, assign queue coverage, triage child-safety reports first, promptly restrict suspected harmful material, take down confirmed violations, record actions, and establish the jurisdiction-appropriate authority-reporting/preservation process with the designated contact. Do not download/forward suspected CSAM as an ordinary support attachment. Report records and private review objects must be included in REL-04's scoped retention/deletion rules; no automatic deletion/preservation legal policy is invented here.

Native Inbox/received moments support content/account reports and account blocks; Profile manages unblock and links to safety/support. Web shared viewing can report by capability without revealing or consuming the link. Reports are bounded, private and deduplicated, with a server identity limit; resetting guest cookies is not a trustworthy anti-abuse boundary. ### Account deletion, policies and retention (REL-04)

This is **locally verified source preparation**, not a deployed deletion service or release approval. Roll out `202610280001_media_controls.sql`, then `202610290001_moderation_safety.sql`, then `202610290002_account_privacy.sql` in order with the matching gateway and maintenance runner. Preserve existing captures; these migrations do not authorize deleting original accounts or content as a test. Native Profile contains deletion independently of public-profile approval, suspension or terms acceptance. `/delete-account` is the external verification/confirmation resource. Both browser apps render shared draft `/privacy` and `/terms`, plus support/deletion resources; native links resolve to the configured product origin.

Deletion requires an Auth-server-verified bearer and a password/OAuth authentication event from the last five minutes. JWT refresh/issuance time, recovery/signup events, editable metadata and supplied account IDs do not establish account control. The browser uses isolated email/password or Google PKCE sign-in, persists only a ten-minute verifier in tab storage, strips callback parameters before IO and requires separate deliberate confirmation. Add the exact product `/delete-account` URL to the intended Google/Supabase redirect allowlist and verify real provider return/cancel/replay before relying on it. Apple-only browser recovery remains unavailable and explicitly blocks release for that provider; a working web verification/recovery route must be supplied before Apple users are invited.

The accepted request atomically disables the account, removes its public profile, tombstones owned moments and revokes grants/links/issued leases. Safety mutations recheck this state inside their transactions. A `202 pending` response is not completed deletion. A private fragment-only receipt checks status without retaining the login; it grants no media access, expires thirty days after completion and must not be logged or placed in a query. Native signout and draft invalidation follow confirmed disabling. Retries recover the same request. Received bytes, recipient copies and forensic device-cache erasure remain outside these controls.

Service-only cleanup waits at least ten minutes, traverses only the queued owner's exact private Storage prefix (including orphan attempts), removes objects and verifies an empty prefix before deleting Auth. Auth absence must be confirmed explicitly; outages/unknown results stay pending. Durable Storage-writer barriers prevent an ambiguous or still-running upload from being treated as finished; successful outbound writes release their barrier. An unresolved writer needs REL-05's restricted reconciliation using actual upstream/process evidence and a fresh sweep, never automatic age-based dismissal. Complete receipts are reswept daily while retained. Batch ordering advances retries without letting a permanently failing oldest request monopolize the queue.

Build the complete maintenance artifact with `node scripts/run-account-cleanup.mjs --build`; it emits `apps/web/.next/maintenance/account-cleanup.cjs`. The product Dockerfile packages it at `/app/apps/web/account-cleanup.cjs` with the traced SDK dependencies. It requires Node 24 and the packaged runtime modules, without a TypeScript compiler or environment files in the image. Run `node apps/web/account-cleanup.cjs` for bounded media/account cleanup and `node apps/web/account-cleanup.cjs --monitor` for the independent watchdog. Both require the environment and secret monitor configuration below. These commands are **not automatically scheduled/deployed**. Never run global maintenance against original local/hosted accounts as a test; generated integration tests scope their destructive work explicitly.

Engineering retention rules: delete owned media instead of keeping a safety copy by default; erase policy acceptance with Auth; scrub associated report/resolution/audit text on deletion; anonymize the removed viewer's identity in other owners' claims/budgets without reopening links or resetting prepaid totals. Other identities and owners are preserved. A restricted expiry transaction removes report/audit records after ninety days from each record's creation. Pending deletions keep only the state needed to retry safely. After cleanup, private status receipts expire at thirty days, but minimal account-ID/time suppression records persist until both a fresh empty-object sweep and **verified backup reconciliation** permit removal. `peekalo_reconcile_deletion_backups(request_id, oldest_recoverable_timestamp)` is owner/admin SQL only (even service-role API access is denied); use it only after inventorying every recoverable snapshot, PITR point and offsite dump, with the oldest remaining point later than cleanup completion. Then the scheduled expiry can remove the aged suppression record. Do not erase this journal merely because thirty days elapsed.

The actual hosted backup inventory/horizon, offsite dumps, provider logs/Auth-audit retention, legal preservation/escalation procedure and a restore drill remain unverified. Supabase database backups contain Storage metadata rather than object bytes; Free projects need a deliberate backup strategy. REL-05 must keep restricted deletion history outside the restored snapshot as necessary, replay accepted restrictions before reopening restored service, reapply newer migrations, sweep associated objects and test that deleted accounts, claims and budgets never reactivate. No fixed backup-erasure deadline or compliance claim is made. See [Supabase backups](https://supabase.com/docs/guides/platform/backups).
